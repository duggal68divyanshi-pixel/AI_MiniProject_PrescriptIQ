# Research Nexus — Research Intelligence Core (Phase 1) + Literature Intelligence (Phase 2) + Scientific Knowledge Extraction (Phase 3)

> **Phase 1 (Research Intelligence Core)** is a complete single-document
> RAG vertical slice. **Phase 2 (Literature Intelligence)**, documented
> starting at [§20](#20-phase-2--literature-intelligence), builds
> multi-paper research projects on top of it: cross-paper chat, structured
> comparison, an automatic literature review matrix, evidence-grounded
> research-gap detection, and research-question generation. **Phase 3
> (Scientific Knowledge Extraction)**, documented starting at
> [§21](#21-phase-3--scientific-knowledge-extraction), adds scientific
> NLP on top of both: section detection, entity/keyphrase/topic
> extraction, claim & limitation extraction, and a lightweight knowledge
> graph — all with full source provenance. This is still **not** the full
> long-term Research Nexus vision (no auth, no Neo4j knowledge graph, no
> AI paper authoring — see
> [Known Limitations](#2012-known-limitations-phase-2-additions),
> [§21.7](#217-known-limitations-phase-3-additions), and
> [Next Development Phase](#22-next-development-phase)).

## 1. Project overview

Upload a research paper PDF. Research Nexus extracts its text, splits it
into overlapping semantic chunks, embeds every chunk into a vector space,
and stores it in Postgres via Supabase + pgvector. You can then:

- **Ask questions in natural language** and get an answer generated by an
  LLM, grounded *only* in the retrieved passages, with page-level source
  citations.
- **Run raw semantic search** and see which passages match a query even
  when the exact wording doesn't appear in the text.

## 2. What this subsystem demonstrates

The complete, real, end-to-end RAG architecture that the rest of Research
Nexus will be built on:

```
PDF → extraction → cleaning → chunking → embedding → pgvector storage
    → semantic retrieval → grounded generation → cited answer
```

Every step is real. There is no mocked vector search, no fabricated
similarity scores, and no hard-coded answers — the LLM step is the only
part that (optionally) calls an external API, and it is fully isolated
behind a provider interface so it can be swapped or run in an offline
`mock` mode.

## 7. Supabase setup

1. Go to [supabase.com](https://supabase.com) → **New project**. Note the
   database password you set.
2. In the dashboard: **Project Settings → Database → Connection string**.
   Copy the URI (use the direct connection, not the pgbouncer/pooling one,
   for local dev) — this is your `DATABASE_URL`.
3. In **Project Settings → API**, copy the **Project URL** and **anon
   public key** — these are `SUPABASE_URL` / `SUPABASE_KEY` (not required
   by this MVP's direct-Postgres access path, but kept for the next phase
   which will add Supabase Auth/Storage).

## 8. pgvector setup

Open the Supabase **SQL Editor** and run both migrations in order:

```sql
-- 1. paste the full contents of supabase/migrations/0001_init_research_core.sql
-- 2. then paste the full contents of supabase/migrations/0002_phase2_literature_intelligence.sql
```

Migration `0001` enables the `vector` extension, creates `documents` and
`document_chunks`, and creates a cosine-similarity IVFFlat index. Migration
`0002` is purely additive: it adds `research_projects`, a nullable
`project_id` on `documents` (`ON DELETE SET NULL`, so nothing breaks if a
project is deleted), `paper_metadata`, `research_analysis` (the Phase 2
analysis cache), and `research_questions`. You can instead run both via
`psql`:

```bash
psql "$DATABASE_URL" -f supabase/migrations/0001_init_research_core.sql
psql "$DATABASE_URL" -f supabase/migrations/0002_phase2_literature_intelligence.sql
```

> **Dimension note:** the migration hard-codes `vector(384)` to match the
> default embedding model. If you change `EMBEDDING_MODEL_NAME` to a model
> with a different output dimension, update the column definition to match
> before inserting any data — pgvector columns have a fixed dimension.

## 13. RAG pipeline explanation

1. The question is embedded with the same local model used for chunks.
2. `retrieval.py` runs `ORDER BY embedding <=> $query LIMIT top_k` — real
   pgvector cosine distance, converted to a `1 - distance` similarity.
3. Chunks below `SIMILARITY_THRESHOLD` are dropped so weak matches don't
   pollute the prompt; if nothing passes, the API returns a clear
   "not enough information" response instead of calling the LLM.
4. Remaining chunks are formatted as numbered `[Source N]` blocks and
   passed to the configured LLM with a system prompt that explicitly
   forbids adding information outside the context and requires citing
   sources.
5. The response is returned with the model's answer plus the exact
   document/page/chunk/similarity for every source used.

## 14. Embedding model explanation

`sentence-transformers/all-MiniLM-L6-v2` is configured by default because it:
- runs fully locally with no API cost or network dependency at query time,
- is small enough (~80MB) to load quickly in local development,
- produces 384-dimensional embeddings that work well for short-to-medium
  passage retrieval (its intended use case).

### Using SciBERT or SPECTER
To use scientific domain models such as **SciBERT** or **SPECTER**, simply update `backend/.env`:

```env
# SciBERT (768 dimensions)
EMBEDDING_MODEL_NAME=sentence-transformers/allenai-scibert_scivocab_uncased
EMBEDDING_DIMENSION=768
```

> **Note**: When changing `EMBEDDING_DIMENSION` from 384 to 768, update the `embedding vector(768)` column definition in your Postgres/Supabase table before inserting data.

Embeddings are L2-normalized at generation time, so pgvector's cosine
distance operator (`<=>`) behaves identically to a dot-product search.

## 15. Chunking strategy

Sentence-aware sliding window (see `services/chunker.py` for full
rationale in code comments):

1. Page text is split into sentences (never mid-sentence splits).
2. Sentences are packed into a chunk up to `CHUNK_SIZE_TOKENS` (~400,
   approximated by word count).
3. Each new chunk starts with the trailing ~`CHUNK_OVERLAP_TOKENS` (~80
   words) of the previous chunk, so facts that sit near a chunk boundary
   remain available as context to whichever chunk best matches a query.
4. Each chunk records the page number of its first sentence for accurate
   citation, even when it spans a page break.

This avoids two common failure modes: giant chunks that dilute embedding
relevance, and hard token-count cuts that split a sentence (and its
meaning) in half.

## 16. Database schema

```
documents
  id, filename, title, status, page_count, error_message,
  created_at, updated_at

document_chunks
  id, document_id (FK), chunk_index, page_number, content,
  embedding vector(384), created_at
  UNIQUE(document_id, chunk_index)
```

Indexes: `documents(status)`, `documents(created_at)`,
`document_chunks(document_id)`, and an IVFFlat cosine index on
`document_chunks(embedding)`.

## 18. Known limitations (Phase 1)

- No authentication — this is a single-tenant local MVP.
- Raw PDF bytes are cached on local disk (`UPLOAD_DIR`) only to support
  re-processing after a failure; there is no object storage integration
  yet (planned: Supabase Storage).
- No OCR — scanned/image-only PDFs with no text layer are rejected with a
  clear error rather than silently producing empty chunks.
- Chunk size is approximated by whitespace word count, not an exact
  tokenizer — close enough for chunk sizing, not exact token billing.
- IVFFlat index quality improves after `ANALYZE`; on a fresh, small
  database recall is still exact-ish because IVFFlat degrades gracefully
  at low row counts.
- Single embedding model per deployment — changing models requires a
  fresh migration (dimension is fixed per column).

# 20. Phase 2 — Literature Intelligence

### 20.1 What's new

```
Multiple Papers
      ↓
Project Knowledge Base       (research_projects + documents.project_id)
      ↓
Cross-Paper Retrieval        (project_retrieval.py — pgvector, scoped to a project)
      ↓

      ↓

      ↓
Literature Matrix            (literature_matrix.py — per-paper structured findings)
      ↓
Gap Detection                (gap_analysis.py — evidence-grounded, cached)
      ↓
Research Questions           (research_questions.py — derived from detected gaps)
```

### 20.2 Architecture

Phase 2 reuses every Phase 1 building block — `embeddings.py`,
`llm_provider.py`, the pgvector `document_chunks` table — and adds a
project-scoped layer on top:

```
                ┌────────────────────────────┐
                │   React "Research Projects"│
                │   tab (ProjectsApp)        │
                └──────────────┬─────────────┘
                               │ REST API
                ┌──────────────▼─────────────┐
                │  /api/projects, /api/…      │
                │  (projects.py, research.py) │
                └──────────────┬─────────────┘
          ┌────────────────────┼─────────────────────┐
          ▼                    ▼                      ▼
 project_retrieval.py   literature_matrix.py    gap_analysis.py
          │                    │                      │
          ▼                    ▼                      ▼
     pgvector search    per-paper structured    LLM synthesis over
     scoped by          extraction (cached      pre-extracted,
     project_id          per paper)              evidence-grounded
          │                    │                 structured findings
          └────────────────────┴──────────┬───────────┘
                                           ▼
                              research_analysis (cache table)
```

Gap analysis is deliberately **not** "dump every paper into the LLM and ask
for gaps". The pipeline is: indexed papers → literature matrix rows
(structured, evidence-grounded per-paper findings) → collect
limitations/methods/datasets across papers → LLM synthesis over that
*concise, already-grounded* structured data → gaps. `evidence_strength`
(`High`/`Medium`/`Low`) is computed in Python from how many distinct papers
actually support each gap (≥3 papers = High, 2 = Medium, 1 = Low) — it is a
real, computed heuristic, not a fabricated statistical score, and it's
labeled "Evidence Strength" in the UI rather than implying a p-value.

### 20.3 Database changes

See `supabase/migrations/0002_phase2_literature_intelligence.sql` for the
full DDL. Summary:

| Table | Purpose |
|---|---|
| `research_projects` | A named collection of papers around one research topic |
| `documents.project_id` | Nullable FK added to the existing table (`ON DELETE SET NULL`) — a document not in any project behaves exactly like Phase 1 |

| `research_questions` | RQs generated from a specific `research_analysis` (gap analysis) row |

### 20.6 Hallucination control

Every Phase 2 LLM call uses its own strict system prompt (see
`metadata_extraction.py`, `project_chat.py`, `literature_matrix.py`,
`comparison.py`, `gap_analysis.py`, `research_questions.py`) that requires:
using only the supplied evidence; explicitly saying "Not reported in the
indexed text" / "insufficient evidence" rather than guessing; and, for gap
analysis specifically, dropping any gap whose `affected_papers` doesn't
match a real paper in the project (see `gap_analysis.py`'s post-parse
filter). No feature ships hard-coded example output — every response
requires actual indexed papers and a working LLM provider.

### 20.7 Performance / caching

- Metadata extraction runs once per document, right after indexing.
- Literature matrix rows are cached **per paper** (`analysis_cache.py`
  keyed on `[document_id]`), so adding one new paper to a project only
  extracts that one paper, not the whole set again.
- Comparisons and gap analyses are cached per **exact set** of document
  ids analyzed; re-opening Gap Analysis or Compare with the same papers
  reuses the previous result instead of re-calling the LLM. Pass
  `force_refresh: true` (gap analysis, research questions) or
  `?force_refresh=true` (literature matrix) to bypass the cache.

### 20.8 Error handling

`InsufficientPapersError` (422) covers: comparing with an unindexed paper
selected, gap analysis / research questions with fewer than 2 indexed
papers. `AnalysisFailedError` (502) covers LLM/provider failures during
comparison, gap analysis, or research-question generation, with the
underlying error message included. `ProjectNotFoundError` /
`DocumentNotFoundError` (404) cover missing projects/documents. The
frontend surfaces each of these as an inline message in the relevant tab.

### 20.12 Known limitations (Phase 2 additions)

- Metadata extraction, literature-matrix extraction, comparison, and gap
  analysis are all one-shot structured-output LLM calls parsed with a
  regex + `json.loads` — a provider that returns malformed JSON causes
  that step to fail gracefully (skipped/error state), not a hard crash,
  but there's no retry-with-repair loop.
- Literature matrix / comparison quality depends on the underlying paper
  having those fields (methodology, dataset, etc.) findable in its
  earliest indexed chunks and top-retrieved passages — a paper with an
  unusual structure may show more "Not reported in the indexed text"
  fields than a well-structured one.
- No knowledge-graph or citation-network layer — "research landscape" here
  means retrieval + structured extraction + LLM synthesis over a project's
  own indexed papers, not a graph of citations between them.
- Gap analysis and comparison are cached per exact document-id set; if a
  paper is removed and a similar-but-different set is re-analyzed, that's
  treated as a new analysis (correct, but means no partial-cache reuse
  across different subsets).
- No authentication/multi-tenancy, same as Phase 1.

## 21. Phase 3 — Scientific Knowledge Extraction

Phase 3 adds a scientific-NLP layer on top of Phases 1 and 2. It turns raw
paper text into structured, provenance-tracked scientific knowledge:

```
Research Papers
  → Section Detection → Entity Extraction → Keyphrase/Topic Extraction
  → Claim & Limitation Extraction → Relationship Derivation
  → Structured Knowledge (Postgres) → feeds RAG, Literature Matrix, Gap Analysis
```

Nothing in Phase 1 or Phase 2 changed behavior — Phase 3 is additive
(new tables, new endpoints, new UI tabs) and the literature-matrix/gap-
analysis enhancements described in §21.5 fall back to the exact Phase 2
behavior whenever Phase 3 hasn't been run for a paper yet.

### 21.1 Models & libraries used

| Task | Library/Model | Repository | License | Runs locally |
|---|---|---|---|---|
| Section classification (primary) | Heading-pattern regex + synonym table | — (deterministic, no model) | — | Yes |
| Section classification (fallback) | Embedding similarity, **reuses the Phase 1 embedding model** | `sentence-transformers/all-MiniLM-L6-v2` | Apache-2.0 | Yes |
| Entity extraction (models/datasets/methods/metrics/domains/tasks) | Curated gazetteer + `rapidfuzz` fuzzy matching | [rapidfuzz](https://github.com/rapidfuzz/RapidFuzz) | MIT | Yes |
| Entity extraction (candidate method phrases outside the gazetteer, optional) | spaCy noun-chunking, `en_core_web_sm` | [spaCy](https://github.com/explosion/spaCy) | MIT | Yes |
| Keyphrase extraction | KeyBERT, **reuses the Phase 1 embedding model** | [KeyBERT](https://github.com/MaartenGr/KeyBERT) | MIT | Yes |
| Topic discovery | BERTopic (UMAP + HDBSCAN + c-TF-IDF), **reuses the Phase 1 embedding model** | [BERTopic](https://github.com/MaartenGr/BERTopic) | MIT | Yes |
| Claim/finding normalization | Your configured LLM provider (Anthropic/OpenAI/mock — unchanged from Phase 2), applied only to a pre-shortlisted candidate list | n/a | vendor ToS | No (API) |
| Limitation normalization | Same as above | n/a | vendor ToS | No (API) |

Call `GET /api/system/ml-info` for a live version of this table, including
whether each library is actually importable in your running environment.

**Why not a fine-tuned scientific NER model (e.g. "SciBERT NER")?** We
looked. SciBERT itself (`allenai/scibert_scivocab_uncased`) is an
embeddings backbone, not a fine-tuned NER head — using it "because it's
SciBERT" would produce nothing useful without a fine-tuning step, which
Phase 3 explicitly avoids (no training from scratch). Public
SciERC-trained NER models exist but recognize coarse classes (Task /
Method / Metric / Material) that don't reliably separate "SciBERT" (a
MODEL) from "ImageNet" (a DATASET) at the granularity this feature needs,
and lack a maintained pip package or a clearly stated license. The
gazetteer + fuzzy-matching approach is deterministic, explainable, keeps
full provenance, and is trivially extensible (add a line to
`services/ml/gazetteer.py`) — see the docstring at the top of
`services/ml/entity_extraction.py` for the full reasoning.

### 21.2 Model download / setup

Everything above except spaCy's `en_core_web_sm` downloads automatically
the first time it's used (KeyBERT/BERTopic reuse the same
`all-MiniLM-L6-v2` model Phase 1 already downloads on first run — no
separate download). Approximate sizes and cache locations:

| Model | Size | Cache location (default) |
|---|---|---|
| `all-MiniLM-L6-v2` (shared by Phase 1 retrieval, KeyBERT, BERTopic, section fallback) | ~90MB | `~/.cache/torch/sentence_transformers/` |
| `en_core_web_sm` (optional) | ~13MB | spaCy's own package install location |

To install the optional spaCy model:

```bash
python -m spacy download en_core_web_sm
```

If you skip this, set `ENABLE_SPACY_CANDIDATES=false` in `.env` (or just
leave it — the code detects the missing model/library and logs once,
then continues with gazetteer-only entity extraction; nothing crashes).

All models here run on **CPU** by default (`ML_DEVICE=cpu`) — no GPU is
required for any Phase 3 feature. A demo-sized project (5–10 papers)
processes in well under a minute per paper on a normal laptop; the
slowest step is usually the LLM call for claim/limitation normalization,
which is bounded by network latency, not local compute.

To change any model, edit `.env` — no code changes needed:

```bash
KEYPHRASE_MODEL_NAME=            # blank = reuse EMBEDDING_MODEL_NAME
TOPIC_MODEL_NAME=                # blank = reuse EMBEDDING_MODEL_NAME
SPACY_MODEL_NAME=en_core_web_sm
ENABLE_SPACY_CANDIDATES=true
TOPIC_MIN_TOPIC_SIZE=2           # lower = topics form with fewer papers
```

Run the new migration after 0001/0002:

```bash
psql "$DATABASE_URL" -f supabase/migrations/0003_phase3_scientific_knowledge.sql
```

Install the new Python dependencies (already added to
`backend/requirements.txt`):

```bash
pip install -r backend/requirements.txt
```

### 21.5 How this improves Phase 2

- **Literature matrix** (`services/literature_matrix.py`): if Phase 3
  extraction has already run for a paper, its structured
  models/datasets/methods/metrics/limitations/results are handed to the
  LLM as a starting point, so the LLM fills in only the genuinely
  narrative fields (research problem, methodology description,
  contributions) instead of re-deriving everything from raw chunks. Falls
  back to pure Phase 2 behavior when Phase 3 hasn't run.
- **Gap analysis** (`services/gap_analysis.py`): limitations that repeat
  across multiple papers (from `paper_limitations`, aggregated by
  `services/project_knowledge.py`) are surfaced to the LLM as explicit,
  counted evidence, on top of the existing structured-findings block.

### 21.6 Demo procedure

1. Open a project with 5–10 indexed papers.
2. Open **Paper Intelligence**, pick one paper, click **Analyze This
   Paper**. Review sections, models/datasets/methods/metrics, keyphrases,
   claims, limitations, and derived relationships.
3. Open **Knowledge Explorer**, click **Analyze All Papers**. Wait for
   background jobs to finish (poll or just refresh after a minute).
4. Click an entity (e.g. a model name) to see every paper/page it's
   mentioned in with source context.
5. Review **Research Topics** — click one to see its representative
   papers and keywords.
6. Review **Project Knowledge** — aggregated models, datasets, methods,
   metrics, common limitations, and key findings.
7. Open **Research Gaps** and re-run analysis — notice the repeated-
   limitations evidence is now grounded in structured extraction, not
   just each paper's LLM-summarized limitations field.
8. Ask the Research Assistant: *"Which methods dominate this research
   area, which datasets are most commonly used, and what limitations
   appear repeatedly?"* — it answers using RAG over the indexed chunks;
   cross-reference against the Knowledge Explorer's aggregated view.

### 21.7 Known limitations (Phase 3 additions)

- Section detection relies primarily on papers announcing their own
  structure via headings; a paper that uses unconventional or absent
  headings will lean more on the embedding-similarity fallback, which is
  a real classifier but less precise than a heading match (its confidence
  score is reported so this is visible, never hidden).
- Entity extraction is gazetteer-based, not a trained scientific NER
  model (see §21.1 for why) — it will not detect models/datasets/methods
  it doesn't know about. The gazetteer (`services/ml/gazetteer.py`) is
  intentionally easy to extend; the optional spaCy candidate pass
  surfaces some out-of-gazetteer method phrases at lower confidence, but
  isn't exhaustive.
- BERTopic needs a minimum of ~3 distinct papers to form any topic at
  all; very small or highly similar projects may return zero topics
  (reported honestly, not padded with fabricated topics).
- Claim/limitation extraction quality depends on the candidate
  shortlisting regex/cue-word heuristics finding good candidate sentences
  in the first place — a paper phrasing its results/limitations very
  unusually may yield fewer candidates than a conventionally-written one.
- Relationships are derived deterministically from section context (a
  model mentioned in Methodology → "proposes", a dataset anywhere →
  "evaluates_on", etc.) — this is a reasonable heuristic, not a learned
  relation-extraction model, and is stored in plain Postgres tables (not
  a graph database) exactly as scoped for this phase.
- As with Phase 1/2, no authentication/multi-tenancy.
